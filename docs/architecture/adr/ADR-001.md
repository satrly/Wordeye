# 001. Использовать монолитную архитектуру вместо микросервисов

Дата: 2026-09-25

## Статус

Принято

## Контекст

Мы делаем приложение для изучения языков по скриншотам: пользователь
присылает скрин, система распознаёт слово, вытаскивает фразу с контекстом
и генерирует карточку для запоминания. На старте выделяются такие
модули/потоки: приём и обработка изображений (OCR), извлечение слова
и контекста, генерация карточек, работа с пользователями.

Команда состоит из 2 человек. Продукт ещё не подтвердил product-market fit,
нагрузка неизвестна, требования будут часто меняться в первые месяцы.
Нет отдельного DevOps-ресурса для поддержки распределённой инфраструктуры
(деплой, мониторинг, трассировка между сервисами, отдельные БД и т.д.).

## Решение

Мы будем разрабатывать приложение как монолит — единое приложение
с чётким разделением на внутренние модули (image-processing, extraction,
cards, users), но с одной кодовой базой, одним деплоем и одной базой данных.

## Последствия

**Плюсы:**
- Быстрая разработка и деплой силами 2 человек, без накладных расходов
  на межсервисную коммуникацию.
- Проще дебажить и тестировать — всё в одном процессе.
- Меньше инфраструктурных решений на старте (один сервис, одна БД,
  один CI/CD пайплайн).
- Легче менять границы модулей, пока продукт ещё нащупывает форму.

**Минусы / риски:**
- Если OCR-обработка станет тяжёлой по ресурсам (например, много
  запросов на распознавание), она будет масштабироваться вместе со
  всем приложением, а не отдельно.
- При росте команды монолит может стать источником конфликтов
  в код-базе и медленнее собираться/деплоиться.
- Понадобится дисциплина в поддержании модульности внутри монолита
  (чёткие границы между OCR/extraction/cards/users), иначе выделить
  сервис в будущем будет больно.

**Что пересмотреть в будущем:** если OCR-обработка станет узким местом
по нагрузке или потребуется независимое масштабирование — рассмотреть
вынос её в отдельный сервис (см. будущий ADR, если он появится).
